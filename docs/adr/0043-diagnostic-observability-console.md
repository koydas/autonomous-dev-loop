# ADR-0043: Diagnostic observability console

- **Date:** 2026-10-20
- **Status:** Accepted

## Context

The dashboard (ADR-0027 amendment, ADR-0040, ADR-0041, ADR-0042) published every recorded fact — runs, events, spans, LLM calls, costs, eval runs — but organised by data source (activity feed, traces, health tables, flow map). Answering "is the system working, where and why not, what to fix first" took reading several pages and interpreting raw counts. Two presentation choices actively hid information:

- The flow map icon of a step was the outcome of its **latest** execution (`stageStatus()`): Review failed, failed, then succeeded showed ✓, with no trace of the two failures on the card.
- Execution status and business decision were conflated in one icon: a review span closed as `success` with a `WITHHELD` verdict showed ✓. On the retained sample (90 runs, 2026-10-16 → 20), 52 of 66 verdicts were `WITHHELD`, 64 of 66 reviews saw a cut diff, and 14 PR heads were reviewed twice (push + pull_request) — none of which was visible on the home page.

## Decision

Reorganise the static site into **Overview → Diagnostics → Pipelines → Investigation** (+ Metrics, the former Health page), with a strict data / diagnosis / presentation split. All pure modules, c8-gated:

- `scripts/lib/pipeline_journey.mjs` — per work item, every attempt of every canonical step (Validation, Code generation, PR preparation, Review, Auto-fix) with its **execution status** (stage span outcome: success / failed / skipped / not recorded) and its **decision** (the journal event: verdict, rejection, block, push, …) side by side; the final attempt, failure and adverse-decision counts, automatic recovery, escalations, and the item's *last recorded state*. Conditional steps say why they are absent (no linked issue; auto-fix not triggered without REQUEST_CHANGES). Running is not observable (records are written on completion) and merge is not journaled: neither is inferred.
- `scripts/lib/pipeline_kpis.mjs` — the overview indicators, each shipped with its definition (source, method, period, population, known limits). A missing population yields `null`, never a default.
- `scripts/lib/pipeline_diagnostics.mjs` — fixed, deterministic rules (no LLM) with named thresholds (`RULES`): failed runs, repeated stage failures, withheld reviews and cut diffs, duplicate reviews of one head, PRs stuck without approval, ineffective auto-fix, blocked generation, provider fallbacks, 429 waits, stage duration regressions, escalations. Each finding carries the observed `fact`, an optional `hypothesis` (rendered as "interpretation, not verified"), impact, frequency and capped evidence (run, event, summary, https source link). Telemetry gaps are listed as "insufficient data", never as health; the status is `no_data` without runs and "no problem detected" says it is not proof of health.
- `scripts/lib/console_views.mjs` — rendering of the overview block (home page), the Diagnostics page, the journey panel (trace page), key events and per-step status/decision (run page), a URL-synced filter bar and the browser-side PR state loader shared by Overview and Pipelines.

The Pipelines page (`flow_dashboard.mjs`, ADR-0042) lists **every recorded work item** (not only merged PRs), shows the final status icon per step plus ×N attempts, an amber ring when the step completed with an adverse decision, and the full attempt history on expansion. GitHub's PR state (`pulls?state=all`, ≤ 10 pages, 5-minute `sessionStorage` cache) is laid over it: `merged_at` → merged, closed without it → closed unmerged, open → open; a recorded PR number takes precedence over a branch/closing-reference hint, so one PR never lands on two items. Merged PRs without a recorded flow still get a card.

Navigation: Overview · Diagnostics · Pipelines · Investigation · Metrics. Every existing page, table and JSON file stays; the full event journal moves behind a disclosure on run pages, after the key events.

### Visual design (2026-10-20, from the design mockup in the README)

- Console shell (`dashboard_ui.mjs`): dark theme by default (light on demand, stored per browser, applied before paint), top tabs with icons, a sidebar with the sections and page filters (status, stage reached, LLM provider facets over the pipeline lists), a phone tab bar with a More menu, "Updated …" from the build time and the findings count on the Diagnostics link (both filled by `assembleSite`).
- Overview (`console_overview.mjs`): windowed indicators (`computeWindows`: 7 / 14 / 30 days ending on the latest recorded run, all precomputed; a select shows one) with change vs the previous window and sparklines, results / duration / provider charts, issue cards, recent pipelines.
- Pipelines rows (`flow_dashboard.mjs`): one table row per work item that opens into stage boxes and key information; the same rows serve the Overview.
- Trace page: tabs (Overview, Timeline, LLM calls, Events, GitHub Actions, Traces), progressive enhancement over plain sections.
- With pipeline views, the base and component CSS ships once in `pipeline/console.css` instead of inline on each of the ~120 pages (site 4.42 MB, was 4.33 MB before the console); an eval-only build keeps it inline.

Deviations from the mockup, by data: no **Running** status or count (records are written on completion); **Success rate** became the review approval rate (no run failed in the sample, so a job success rate reads 100 % and hides the withheld reviews); PR titles come from the GitHub API in the browser (titles are not in the public record); Groq shows "free tier" with its share of calls next to its 0 % share of cost; the status badge never says "healthy", only what the rules found.

## Alternatives Considered

- **A front-end framework (React/Vue) or a hosted observability backend**: rejected — the site is a static Pages build from the `metrics` branch with no credential (ADR-0027, ADR-0042); a framework adds a build chain for no capability the inline scripts lack.
- **An LLM-written diagnosis**: rejected — every problem worth reporting is a deterministic pattern over recorded events, and a generated explanation could present a hypothesis as fact.
- **New producer-side fields** (separate execution status / decision, a merge journal): deferred — the producer change is tracked in `docs/dashboard-partial-diagnosis.md`; the console derives both from existing events without touching the pipeline.

## Consequences

- ✅ The home page answers "is it working" with a status, six indicators that each link to their explanation, the main problems and the items waiting on a person.
- ✅ Intermediate failures and adverse decisions are visible on the collapsed card and listed per attempt; execution status and decision are never conflated.
- ✅ Every indicator and finding is traceable to the runs and events it was computed from.
- ⚠️ "Last recorded state" can be stale: a person may already have acted (labels, merge). Overview and Pipelines re-check merges live; label state is not recorded.
- ⚠️ Rules have fixed thresholds: below them a pattern is not reported. Duration trends need ≥ 3 runs in each of the two latest 7-day periods; otherwise the gap is stated.
- ⚠️ Dark by default: a reader who prefers light switches once per browser.
- ⚠️ Windows are relative to the latest recorded run, not to the build time: after a quiet week the "last 7 days" are the last 7 days with data, as the subtitle states.

## Amendment (2026-10-20): guardrail outcomes are not anomalies

On the first real data (`metrics` branch, October 2026) the two loudest warnings were guardrails doing their job: 66 of 80 verdicts WITHHELD, every one with code cut to the Groq review budget (ADR-0038), and 4 auto-fix attempts without a push, each stopped by a protected target (ADR-0021) or by files the budget withheld from the prompt (ADR-0029). A warning that fires on designed behaviour hides the real anomalies among them.

The `review-withheld` and `autofix-ineffective` rules now classify each case, and the share thresholds (`withheldShare`, `autofixNoPushShare`) apply to the **anomaly share**. The total share still decides whether the card is shown, so the volume stays visible; the severity is `warning` only above the threshold on anomalies, `info` otherwise, with the ADRs of the guardrails observed in the title.

- **Review** — each WITHHELD verdict keeps its cause from `withheldCause()` (`pipeline_health.mjs`, the Metrics page's split), the provider whose answer it is (the run's last non-failed review call) and the input budget its prompt was cut to (`review.prompt_truncated.max_input_tokens`). Guardrail: a code cut (`approve_cut`, `cut_unknown`, ADR-0038) or missing / stale CI evidence (ADR-0026). Anomaly: REQUEST_CHANGES withheld on unseen code (`rc_unseen`), an unknown cause (`other`), and a fallback answering a prompt cut to the primary's budget (a budget is set only by a budgeted provider: the fallback saw no more than Groq would have, cf. #242), unless missing / stale CI evidence withheld it, which stays a guardrail. Distinct heads are keyed by PR and SHA. The fact counts verdicts, distinct PR heads and PRs (WITHHELD does not dedup, ADR-0028), and lists responding providers and budgets.
- **Auto-fix** — an attempt is blocked by design when every rejected rule is `protected_path`, `unshown_file` or `withheld_file`; or when it proposed no change while `autofix.prompt_budget.hidden_files` was not empty. Anything else without a delivered push is an anomaly. Skip reasons and evidence come from the attempts only. A run stopped on an approved head (ADR-0028) or at the attempt limit (ADR-0034) exits before `autofix.start`: it is not an attempt and never counts as one, push or anomaly.

⚠️ The records do not name the files a `no_changes` attempt needed (the model returned `changes: []`): "files withheld by budget" is the closest observable cause, not proof that the needed files were among them. A `no_changes` on a false finding in a PR that also had hidden files reads as blocked by design. No producer or record change.

## Amendment (2026-10-21): findings have a lifecycle

A rule is evaluated over the whole retained window, so a problem fixed at the source stayed a `warning` until its history aged out (on the October 2026 data: "Review diffs are cut" at 88 % and "Same PR head reviewed more than once" after the review moved to Anthropic, with 11 clean reviews since). Every finding now carries `first_seen`, `last_seen` and a `status`: `active` while the pattern occurs in the last `RULES.activeWindow` (10) runs its rule could have fired on, `resolved` otherwise. A resolved finding is `info`, titled "… — resolved since <date of the first clean run>"; the historical numbers stay in `fact` and `evidence`, and a new occurrence makes it active again. The guardrail / anomaly split extends to `review-coverage` (cut + WITHHELD is ADR-0038; cut + APPROVE is impossible since ADR-0038 and `critical`) and `review-duplicates` (a second run after a WITHHELD verdict or as a manual re-run is ADR-0028; two runs on one head that the marker skipped neither is the push / pull_request race). The Overview "Issues requiring attention" lists active warning / critical findings only; resolved ones stay on the Diagnostics page. A rate rule (`review-withheld`, `review-coverage`, `autofix-ineffective`, `codegen-blocked`) fires on its whole-window rate **or** on the rate it had up to its last occurrence, so clean runs that dilute the rate under the threshold turn the finding into `resolved` instead of making it vanish; a pattern that never reached the threshold stays unreported. The severity of `review-withheld` and `autofix-ineffective` is judged on the anomaly share of the active window.

## Amendment (2026-10-21): an escalation is a queue, not a finding

On the October 2026 records the `escalations` finding listed 7 work items. Checked on GitHub, one still waited on a person (issue #200); three PRs were merged, five issues or PRs closed, one approved since. The 10 escalations recorded all came from a protected or withheld target (`code_gen` blocked with `source: model` and `hidden_files`; auto-fix `no_changes` with files withheld by the budget, or `guardrail_rejected` on `protected_path`): the human gate working (ADR-0001), not an anomaly. `itemState()` read run records only, and a closing or a merge produces no run, so an item stayed `escalated` for ever and the finding could not tell a wait from a leftover.

- **The end of an item is journaled.** `item-closed.yml` (`issues: closed`, `pull_request: closed`) runs `scripts/item_closed.mjs`, which writes one `item.closed` event through `observability.mjs` and commits the run record to the `metrics` branch like every other run (ADR-0040, ADR-0041: the work item comes from the event payload). Published meta: `state_reason` (issue) or `merged` (pull request), nothing else (`EVENT_META_ALLOWLIST`). The workflow has no LLM secret and no `AI_PR_TOKEN`; its one write scope is `contents: write` for the `metrics` branch; its scripts come from the default branch, never from a pull request tree (ADR-0023). It opens no stage span, and `isLifecycleRun()` keeps such runs out of the execution indicators and the diagnostic rules.
- **`itemState()` takes it into account.** `merged` and `closed` are states of their own and prevail over every other state, `escalated` included. A merged PR ends the item; a closed issue ends it; a PR closed without a merge ends it only when it is the item's own (a PR without issue) or its latest PR, so replacing PR 10 by PR 11 does not close the issue. A run of any step that started after the closing means the item was reopened: the closing no longer counts.
- **"Waiting on you" (Overview) replaces the escalation card.** One row per open work item whose last state is `escalated`, oldest first: item, step, the reason in plain words with the protected or withheld files named (`hidden_files`, `shown_files`, `autofix.file_withheld`, the write-guard `rules`), the escalation comment, and since when. No severity: a wait is not a problem. `pipeline_waiting.mjs` (pure) builds it from the journeys and the run records.
- **The `escalations` finding is kept for what the design does not explain**, `warning`, over the open items only: `no_changes` although a file was shown that the repository's denylist (ADR-0044; the hard floor when the build cannot read it) does not protect; a patch rejected for its content (a rule other than `protected_path`, `unshown_file`, `withheld_file`); an error of the stage before the escalation; a reason or a prompt budget the record does not give. Designed: a protected or withheld target, a blocked generation (`denylist`, `model`, `notes_only`), the attempt limit (ADR-0034).
- **Telemetry gap, not inference.** Items closed before the workflow existed have no `item.closed`. They are listed in Diagnostics → data gaps (`closure-before-journal`) and stay `escalated`; the dashboard never reads silence, or the PR state on GitHub at build time, as a closing. The Pipelines page keeps its live GitHub overlay for pull requests.

Consequences. The workflow belongs to this repository: a target repository (ADR-0045) gets the queue and the finding but no closing until a reusable `adl-item-closed.yml` and a caller template exist. Every closing of an issue or PR of the repository writes a record, pipeline item or not, so a human PR appears on the Pipelines page as a closed item without steps. A pull request from a fork has a read-only token: its closing is not recorded (the step warns, the run does not fail). `codegen-blocked` ("Code generation is mostly blocked") still counts designed blocks and is not changed here.

## Amendment (2026-10-24): the home is one phone screen

The home had grown to about 5,800 px at 375 px wide (nine screens on an iPhone 13 mini) and said several things twice: the status badge, the "Issues requiring attention" cards and the Diagnostics badge named the same problems; the "Waiting on a person" strip, the "Waiting on you" list and the Recent pipelines filter the same items; the result, duration and provider charts redrew the indicators above them; Recent pipelines was the head of Pipelines. The evaluations, one of the three questions the page answers, came last.

- **The home answers three questions in one screen (375 × ~630 CSS px):** are the flows going through, what do they cost, is the quality holding. One status line (the diagnostic status and the most severe active problem, linked to its card), then four rows over the last 7 days: **Flows** (runs, segmented by class; approval rate; work items by latest state), **Cost** (list price, per stage), **Quality** (eval gates passing, one chip per suite: headline score, gate, trend against the previous run on the same dataset), **Waiting on you** (count, the three oldest). `consoleOverview()` in `scripts/lib/console_overview.mjs`.
- **Overview, then drill-down.** Each row opens its page (Pipelines, Metrics → cost, Evals, Pipelines → Waiting on you); each chip opens a filtered view (`flows.html?state=…&period=7`, a finding's card, a suite's panel on `evals.html#suite-<name>`, a trace). A chip's count is the length of the list it opens: the Flows chips count work items by latest state with the Pipelines filter's own predicate and period rule (`periodItems`), not runs — a run class (adverse) is not an item state (a REQUEST_CHANGES item is `changes_requested`, outside `attention`). The run-class bar links nowhere.
- **A change is shown only on a populated base:** at least 10 runs (or 10 verdicts) in the previous window. A percentage on a handful of runs is noise (+3283 % after a quiet week). Amounts have 2 decimals on the home (`shortAmount`); the detail pages keep 4.
- **Nothing is dropped, it moves.** The windowed indicators, charts, secondary strip and metric definitions head **Metrics** (`overviewTrends()`, `health.html#trends`, 7 / 14 / 30 days); the full Waiting on you list heads **Pipelines** (`flows.html#waiting`); problem cards are on **Diagnostics**; the evaluations are **`evals.html`** (an old `index.html#evaluations` link is forwarded). A site without pipeline views keeps the evaluations as its home.
- **Navigation.** Phone tab bar: Overview · Diagnostics · Pipelines · More (Investigation, Metrics, Evals, Models, Trace table, Rules and levers) · **Tools**, the switch to the ai-dev-tools dashboard. The line of links above each page is gone (the nav carries it). Theme: a stored choice, else the system's (`prefers-color-scheme`), dark without either.
- **`status.json`** at the site root: `{ schema_version, app, generated_at, status: ok | warn | bad | no_data, headline }`, the diagnostic status raised to `warn` by a failing eval gate. It is what the companion dashboard shows on its own switch; no finding text is copied.

Consequences. The home reads the scorecard as well as the metrics branch, like `status.json`; both are left out of the "eval half unchanged" check of a pipeline-only build, as `index.html` and `findings.json` already were. The fit in one screen is held by structure (four rows, one line of chips that scrolls sideways) and checked by hand in Chromium at 375 × 629; there is no browser in the test suite.

## Amendment (2026-10-25): external review churn is an observation

**Context.** The loop's own review counts its cycles (`review_cycles`); the external reviewer (Codex) answers every push on its own, and `review_cycles` does not see it. Over the 250 PRs read on 2026-10-24, 19 PRs held 57 % of the 320 external threads, 70 % of them on one file. `external_review` on the approved `pr` record (`metrics/runs.jsonl`) holds the counts, but Diagnostics reads the published run records, not that file.

**Decision.**
- An approving run journals `review.external` (`prNumber`, `rounds`, `threads`, `p0p1`), counts only, through `EVENT_META_ALLOWLIST`; no login, comment body or title. Not emitted when GitHub could not be read: unknown is never 0.
- Rule `external-review-churn` (category Review): PRs whose newest highest `rounds` reaches `RULES.externalRounds` (3). It is always `info`, so it never raises the dashboard status: the loop does not control that reviewer, and the counts are a lower bound (the reviewer answers a head after the run that recorded them). It resolves like any rule (`RULES.activeWindow`). The hypothesis names a possible cause (each round finds a neighbour of the previous fix) and says it is not verified; the records hold no finding text.
- No lever (`NO_LEVER`): the practice that shortens it is `AGENTS.md`'s (fix the class, not the instance; keep a PR small), not a setting, and a lever applies to `warning` / `critical` findings only (ADR-0047).

**Not done.** Active lessons (ADR-0051) take no signal from this: they carry closed ids written by code, and the external findings are free text from a third party; a classifier of their titles would make a text the model could be steered by cross into a prompt.

## Amendment (2026-10-25): conflicts-fix on the dashboard (ADR-0059)

The new stage is read by the same pure modules, nothing else changes. `pipeline_journey.mjs` gains a sixth step, **Conflicts fix** (`optional: true`): its decision comes from `conflicts.resolved` / `.escalated` / `.skipped` / `.error`, a successful merge after a conflicts-fix escalation settles the item (as an APPROVE settles a review escalation), and the flow card draws the step only on an item where it ran (an icon "not recorded" on every card that never conflicted says nothing). `pipeline_waiting.mjs` explains a `conflicts.escalated` reason: a structural limit (protected path, unsupported or binary file, size, file count, registry change, token scope) is `by_design`, a post-check, write-guard, parse, npm or push failure is not; the record names no file. `pipeline_diagnostics.mjs` adds the rule `conflicts-unresolved` (attempts without a merge commit; `warning` only when the stage's own failures reach `conflictsUnresolvedShare`, otherwise `info` "left to a human by design"), with its lever in `meta_levers.mjs` ([ADR-0047](./0047-findings-export-and-lever-table.md)); `llm_cost.mjs` maps the `conflicts` LLM stage to its pipeline stage.
